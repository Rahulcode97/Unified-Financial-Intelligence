Flagship case study · Designed, built & operated end to end

From blind outreach in spreadsheets to a research intelligence platform.

Marketing used to reach academic researchers by guesswork: lists in Excel, no idea of who worked on what, no way to tell a department head from a first-year PhD. I built the platform that changed that. It collects from public academic profiles on a fleet of repurposed office PCs, classifies every researcher by department and field, ranks them by work history, and puts the right shortlist in front of marketing. The whole system is operated in plain English.

The problem

The work was manual, and the targeting was blind.

Before writing any code I interviewed the marketing team, the directors and the juniors doing the collection. The bottleneck was not volume. Nobody could say who was worth contacting, and every answer lived in someone's spreadsheet.

Before
  • Contact lists built and merged by hand in Excel, one file per person
  • No field, department or seniority on a record, so campaigns went to everyone
  • The same researcher appeared many times under different spellings
  • Collection was manual browser work by juniors, one machine at a time
  • Spare office PCs sat switched off
  • Infrastructure changes were risky and depended on one person's memory
After
  • One system of record: one identity per researcher, with every sighting and source year kept
  • Every researcher classified into field and subfields, with the department and work history attached
  • Targeted shortlists ranked by research area, output and recency, which lifted the open rate from 8% to 36%
  • 10-PC collection fleet that schedules, self-heals and updates itself
  • Plain-English control: directors and juniors run the fleet by chatting with an ops copilot
  • Guarded deploys: risky database changes are flagged before they reach production

Architecture

Six systems, one pipeline.

Collection, storage, intelligence and targeting form one flow. Operations and safety tooling sit around it. Every service is containerised and self-hosted with Coolify on a Hostinger VPS. I own provisioning, deploys, access and monitoring.

What I built

The components, and the engineering in each.

Each one is a production system with its own repository, release path and access model. I wrote them, deployed them and support them.

01 · DISTRIBUTED COLLECTION FLEET

Idle office PCs, turned into a self-managing fleet →

A Rust desktop agent turns any spare Windows PC into a worker. It runs several browser slots, keeps a local outbox so nothing is lost offline, and reports its free memory, CPU and disk on every heartbeat.

  • PIN-based pairing; each machine then gets its own revocable key
  • A scheduler sends browsers to the job with the most hours left, so no job starves
  • Stalled slots restart automatically; after two failures the work moves to another machine
  • Self-updates from tagged releases; quiet hours and slot caps set per machine
  • ETA estimates from measured throughput in units per browser-hour
Rust · Tokio · AxumWebView2Manifest V3GitHub Actions
02 · RESEARCH INTELLIGENCE HUB

One record per researcher, with confidence you can audit

Researchers are linked to universities, departments, papers and rank. This is where classification, enrichment and identity resolution happen. The ML page covers it in depth.

  • Local classifier first; only uncertain records go to the LLM
  • The LLM fills only empty fields and never overwrites a human's value
  • Duplicate profiles merge only when they share a paper; otherwise a human gets a question
  • Watchdog retries dropped calls and recovers stalled runs
FastAPIscikit-learnReact · TanStack QueryPostgres
03 · OPS COPILOT

Run the whole fleet by chatting with it

Directors and juniors ask "what's stuck?" or "move these departments to another machine" in plain English. The LLM calls the same tools the Fleet page uses, exposed over the Model Context Protocol and REST.

  • Bounds live in code, not in a prompt: no tool can delete data, touch users or keys
  • Every action can be dry-run in a rolled-back transaction first
  • Fleet-wide actions need explicit confirmation and are rate-limited
  • Every action is audit-logged and most can be undone with one click
  • Scoped keys separate data work from fleet control
MCP · JSON-RPCGrokClaude · Cursor compatible
04 · CONTACT INTELLIGENCE PLATFORM

A master contact archive that absorbs huge files safely

The archive keeps one row per contact and every sighting of it in a year-partitioned table, filed in a hierarchical catalogue. It also scores whether each contact is safe to reach.

  • Large workbook imports are queued and replace a period inside one transaction
  • ltree catalogue with rollup tables, so parent pages never scan millions of rows
  • Sendability scoring with per-domain memory: each new contact inherits what the domain has already shown
  • Subject-scoped editor rights, year locks and streaming exports
PostgreSQL 18ltree · pg_trgmReact 19 · Vitepsycopg 3
05 · DEPLOY GUARD

A VS Code extension that knows which SQL is dangerous

I forked and extended an editor extension for the self-hosted PaaS so the whole estate can be operated from the IDE, including behind a zero-trust access gateway.

  • Deploy-risk classifier: reads pending migrations and flags SQL that would lock or rewrite live tables
  • One-click merge, promote and rebuild, with status, logs and restarts in the sidebar
  • Post-deploy check in a headless browser catches pages that return 200 but render blank
  • One extension serves every project in the estate
TypeScript · esbuildPlaywrightCoolify API
06 · STAFF OPERATIONS CONSOLE

Access, accounts and onboarding in one place

The organisation's internal console handles staff accounts, tasks, tools, subscriptions and the steps that bring a person on or off.

  • Five roles with per-user overrides; the API strips fields the caller may not see
  • Credential vault: AES-256-GCM at rest, reveal-on-permission, audited
  • Google Workspace admin automation for user creation, suspension and sync
  • Onboarding and offboarding as step runs that record partial failures

Security & reliability

Built to be trusted with real data.

ConcernHow it's handled
Who can sign inInvite-only Google SSO and passkeys. Unknown accounts are rejected; sign-in never creates a user.
SessionsOpaque tokens stored only as hashes, with expiry, a per-user cap and server-side revoke.
Machines & botsSeparate hashed keys for devices, extensions and bots, each with its own scope. A bot key cannot post collected data.
AuthorisationEnforced on the API, not just hidden in the UI. Role, per-user overrides, subject scope and year locks all apply.
SecretsVault encrypted with AES-256-GCM; plaintext is revealed only with permission and audit-logged.
ReleasesWatch-path deploys per service, migrations recorded per file and run in transactions, browser-level health checks after deploy.
